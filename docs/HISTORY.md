- **Sage export: a reversal and the booking it undoes are left out together (Sep 17 2026):** Owner saw `MV-8303370d` in the August Sage preview — the Sep 9 reversal of a duplicate ONT (West Mountain Region → Owen's Truck), sitting next to the still-unexported duplicate it cancels. The per-row rules keep a Region → truck transfer on purpose (it is a consumption reversal), but with both rows headed for the same file accounting got a consumption line plus a transfer back with a blank PROJECTID (the destination is a truck), which only nets out if someone notices. Owner's call: drop the pair. New pure `findCancelledReversalPairs` + `sageExportableMovements` in `lib/inventory.js` — the ONE decision about a file's contents, used by both `buildSageCsv` and the sheet's preview so they cannot disagree. A pair cancels only on an exact mirror: reversal carries `[reversal:<movement id>]`, both rows in the candidate set and individually exportable, same part, same quantity, endpoints swapped, **same export state** (both unexported or both in one batch). If the original already went to Sage in an earlier batch the reversal exports alone — the only way Sage learns the unit came back. Partial reversals, a second reversal of one original, and reclass markers all stay in the file. The sheet shows an amber "N reversed booking(s) left out" note, and **Download + mark exported stamps the cancelled pair with the batch** even though it is not in the CSV: left unexported it would trip the "unexported movements dated before this window" warning on every later export. Not done (owner chose the pair rule only): filling PROJECTID from the source Region on a lone reversal. Tests: 7.
