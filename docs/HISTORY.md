# FiberLog change history

> Moved out of CLAUDE.md (July 2026). Historical record of major work.

- **Delete chains pre-flight for booked inventory (Sep 3 2026):** Incident on Gigwave › Ninigret, task "calypso ridge 140882": a crew passdown (pending) and the owner's own passdown (approved → 2 × Wave Pro auto-deducted with asset tags) both lost their `log_entries` / `entry_parts` when the owner tried to **delete the task**. The chain in `ProjectManager.handleDeleteTask` (and the three in `AdminPanel`: deletePhase / deleteProject / clearPhaseData) deletes entry_parts → log_entries → submissions → sessions → task; the approved submission is FK-blocked by `inventory_movements.submission_id`, so the chain wiped both passdowns' materials and only THEN threw. `must()` (backlog #42) made the failure honest but couldn't undo the first two steps. Fix: `assertNoBookedInventory(taskIds, label)` in `lib/supabase.js` — counts movements by `task_id` and by the sessions' submission ids and throws a plain-English "Close the task instead" error **before** any delete; wired into all four chains (deleteProject checks every phase up front, not per-iteration). The stuck pending passdown was flagged "superseded by approved passdown"; the ledger was never wrong (the movement + its tags survived).

- **Sonar asset tags on imported transfers (Sep 2 2026):** Owner asked whether the asset-tag field on the Sonar reports could be carried onto the transaction. It already was, invisibly: the asset report's `Model Field Data | Value List` (Sonar path InventoryModels > InventoryItems > InventoryModelFieldData) is a flattened, duplicated, unlabeled bundle — `92858 | CXNK0125B87D | 04:BC:9F:4D:AD:8B | 59995` — and the importer's "first 3+-digit number" item key, stamped as the `[sonar:<n>]` dedup marker on every import since June, **is the physical asset tag** (owner-confirmed). Measured over 40 deliveries / 379 unique units: 283 carry a serial, 356 a MAC, 77 a second trailing number (an older labeling scheme, kept as "Alt tag"), 11 the tag alone. New pure module `lib/sonarAssetIds.js` (`extractItemIdFromValueList` moved here unchanged so the dedup key never shifts; `parseSonarValueList` classifies tokens by shape — MAC = 6 hex pairs or 12 bare hex digits since Calix ONTs print MACs without separators; `formatSonarLineNote`; 14 tests). `SonarImportSheet` writes `line_note` = `Tag N · SN … · MAC … · Alt tag N` on each transfer (from the canonical/longest value list picked by the dedup) and previews it under the part; `recordMovementsBatch` now forwards `line_note` (it was silently dropping the key). Reports → Consumption fetches `line_note`, the CSV gained an **Asset Tag / Serial** column, and By-account cards list one tag line per unit under the SKU. Activity + raw-history CSV already render the column (infra tags, same day). Fiber-jobs report untouched (no equipment field). Backfill: `scripts/backfill-sonar-asset-tags.mjs` regenerates tag → note from archived report CSVs with the same parser and emits one `line_note`-only UPDATE keyed on the exact `[sonar:<tag>]` marker; run against the 62 archived webhook deliveries + the manual June export.

Stored as `entry_parts.line_note` (draft-persisted in `working_counts.partNotes` / inline `lineNote` on extra lines; survives flag-restore), carried through `save_log_entry` + `replace_submission_parts` (manager edit mode has the same input, so a forgotten tag can be added before approval), and `approve_submission` string_aggs the folded lines' notes onto the auto-deduct row as `inventory_movements.line_note` — a separate column, deliberately never appended to the fixed `notes` string the occurred_at backfill keys on. Migration `20260902120000_entry_parts_line_note.sql`.

- **Sage export: consumption-only by default, groups are trucks (Sep 2 2026):** Owner report — "the Sage export is still pulling transfers from location to location … consumption is showing any transaction from a location to a group." Two causes in `isExportableMovement` (`lib/inventory.js`). **(1)** The default mode kept crew loads + returns (warehouse/bin ↔ truck) — the old `strictConsumption` checkbox that dropped them was opt-in "so today's behavior is preserved", and nobody flipped it. **(2)** Even strict mode only tested `type='truck'`, so loads into shared **group** locations (Contractor - RNS, Crew - Construction …, Drop Trailer) passed every rule — a gap `docs/INVENTORY_FLOW.md` had logged as "needs its own sign-off". Measured on the unexported August ledger: the old default exported 718 rows / 61,976 units, of which only 491 rows / 36,711 units actually landed in a Region; the other 227 rows were staging (161 bin→truck, 27 bin→group carrying 24,162 units, returns, group↔warehouse). Fix: `truck` and `group` are now one "staging" class in the filter (`isStaging`); staging↔staging handoffs always drop; warehouse/bin ↔ staging loads/returns drop **by default**; the option flipped from `{strictConsumption}` to `{includeStaging}` (default false) and the sheet checkbox became **Include crew loads & returns (not consumption)**. Also fixed a latent bug in the old strict branch: its unconditional `toType !== 'job_site'` test would have dropped `issue` / `scrap` off a truck (no destination) — the staging rule is now scoped to `transfer` / `return`. Region → staging reversals still export. The Reports → Consumption view and the By-account Sonar report were never affected (they read `getConsumptionLedger`, which already keeps only `to_location.type = 'job_site'`). Tests: `inventory.test.js` gained a `GROUP` fixture and cases for the group leak, the issue/scrap guard, and the opt-in. Docs: BACKLOG #4, INVENTORY_FLOW (gap closed), MANAGER_GUIDE, TRAINING.

- **Auto-deduct dated by submit time (Aug 28 2026):** Owner saw Reports → Passdowns report 936 ft of strand for "This week" while Consumption reported 7,966 ft for the same filters. Cause: Passdowns dates lines by `submissions.created_at`, Consumption by `movementEffectiveDate` (= `occurred_at ?? created_at`), and `approve_submission` never stamped `occurred_at` on auto-deduct movements — so crew consumption was dated by *approval* time. Three passdowns submitted Aug 20–21 and approved Aug 24–28 fell in different weeks on the two views (the Sage export shares the effective date, so month-end approvals were sliding work into the next period). Fix: the auto-deduct INSERT now stamps `occurred_at = v_sub.created_at`; 198 existing rows (42 submissions) backfilled from `inventory_movements.submission_id`, 24 June rows with no submission/task link left NULL. Migration `20260828120000_auto_deduct_occurred_at.sql`, applied live. Verified post-backfill: the same "This week" strand query = 936 on both sides. Reports hint text now says which date each mode uses.
